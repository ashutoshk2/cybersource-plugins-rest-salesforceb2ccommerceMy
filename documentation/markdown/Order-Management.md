# Order Management

---

Salesforce B2C Commerce does not natively support order management functions. This cartridge has functions that can be utilized to process captures, authorization reversals, and refunds.

> **Important:** These functions are not available to use in the Salesforce B2C Commerce UI without customisation. They are building blocks that a merchant can call from a custom controller, job, or Service Order Management (SOM) integration to implement their own order-management workflow.

---

## Capture

The capture function can be found in the script `scripts/http/capture.js` and there is a working example in the `ServiceFrameworkTest-TestCaptureService` controller.

Reference the capture.js object and make the call as follows:

```javascript
var captureObj = require("~/cartridge/scripts/http/capture.js");
var serviceResponse = captureObj.httpCapturePayment(requestID, merchantRefCode, paymentTotal, currency);
```

The resulting `serviceResponse` object will contain the full response object generated by the request. The contents of this object will determine your logic in handling errors and successes.

### Capture Request Parameters

| Parameter | Description |
|-----------|-------------|
| requestID | The Cybersource Request ID from the initial authorization |
| merchantRefCode | The Salesforce Order Number |
| purchaseTotal | The capture amount |
| currency | Currency Code |

### Function Signature

```javascript
httpCapturePayment(requestID, merchantRefCode, purchaseTotal, currency)
```

## Refund

The refund function can be found in the script `scripts/http/refund.js` and there is a working example in the `ServiceFrameworkTest-TestRefundService` controller. It issues a refund against a **captured** payment using the Cybersource Refunds REST API (`refundCapture`), and supports full, partial, and multiple partial refunds.

Reference the refund.js object and make the call as follows:

```javascript
var refundObj = require("~/cartridge/scripts/http/refund.js");
var serviceResponse = refundObj.httpRefundPayment(transactionId, merchantRefCode, paymentTotal, currency);
```

The resulting `serviceResponse` object will contain the full response object generated by the request. The contents of this object will determine your logic in handling errors and successes.

When the captured total is known on the order's payment transaction, a requested amount that exceeds the remaining refundable balance is rejected (recorded as a failed attempt) before the gateway call, so the order can never be over-refunded across multiple partial refunds.

The gateway outcome is mapped onto the order's payment transaction custom attributes `refundStatus`, `refundedAmount`, and `remainingRefundable`. Every attempt and outcome is recorded in an order note ("Refund Processed" on success, "Refund Failed" on failure) and in the `cybersource`/`refund` audit log. The request includes `clientReferenceInformation.applicationName`, `applicationVersion`, and the partner PSID (`partner.solutionId`).

### Refund Request Parameters

| Parameter | Description |
|-----------|-------------|
| transactionId | The Cybersource capture ID the refund is issued against |
| merchantRefCode | The Salesforce Order Number |
| paymentTotal | The refund amount |
| currency | Currency Code |

### Function Signature

```javascript
httpRefundPayment(transactionId, merchantRefCode, paymentTotal, currency)
```

> **Metadata:** the refund tracking attributes `refundedAmount` (double), `remainingRefundable` (double), and `refundStatus` (string) are added to the **PaymentTransaction** system object (which belongs to the order). Re-import the cartridge metadata so these attributes are available.

## PayPal & Venmo (eWallet)

Capture, authorization reversal, and refund for **PayPal** and **Venmo** orders use the
**same building blocks** above — `httpCapturePayment`, `httpAuthReversal`, and
`httpRefundPayment`. You do not call any PayPal-specific function.

PayPal and Venmo are processed by Cybersource as alternative payment methods (eWallets),
which require two extra fields on the order-management request that card transactions do
not: `processingInformation.actionList` and `paymentInformation.paymentType`. These are
added automatically by the `app.payment.modifyrequest` hook
(`scripts/hooks/payment/modifyRequest.js`), which all three building blocks already invoke.
The hook looks up the order from the request, and **only** when the order's payment
instrument is `PAYPAL` or `VENMO` it sets:

| Operation | actionList | paymentType.name | paymentType.method.name |
|-----------|------------|------------------|--------------------------|
| Capture | `AP_CAPTURE` | `eWallet` | `payPal` / `venmo` |
| Authorization Reversal | `AP_AUTH_REVERSAL` | `eWallet` | `payPal` / `venmo` |
| Refund | `AP_REFUND` | `eWallet` | `payPal` / `venmo` |

For credit card and every other payment method the hook returns the request unchanged, so
their behavior is identical to before. No new site preferences or custom attributes are
required, and the existing `capture.js` / `authReversal.js` / `refund.js` scripts are not
modified.

> The `app.payment.modifyrequest` hook is registered in `int_cybs_sfra_base/hooks.json`.
> If you maintain your own copy of `hooks.json`, ensure this entry is present, otherwise
> PayPal/Venmo order-management requests will be sent without the required eWallet fields
> and rejected by Cybersource.
